## 3. Chọn cách cập nhật dữ liệu

**Muốn bộ mẫu mới đồng nhất: tạo database demo rỗng riêng.** Giữ nguyên database cũ để quay lại. Chọn MỘT trong hai cách nạp sau:

### Cách A: tạo từ code seed

Trong thư mục BE, cấu hình `DATABASE_URL` và `DIRECT_URL` cùng trỏ tới database demo mới. Với Supabase, hai chuỗi có thể khác host/cổng pooler nhưng phải cùng project/database/schema. Kiểm tra đích kết nối trước khi chạy.

```powershell
npm ci
npx prisma generate
npx prisma db push
npm run db:seed
npx ts-node test/seed-lifecycle.check.ts
```

Không cần `--reset` vì database mới đang rỗng. Nếu `db push` cảnh báo mất dữ liệu hoặc yêu cầu reset, dừng và kiểm tra lại kết nối; không thêm `--accept-data-loss` hay `--force-reset`.

### Cách B: khôi phục snapshot đã kiểm chứng

Dùng PostgreSQL client 16 trở lên, tạo một database demo **rỗng**. Chạy từ thư mục gốc workspace bằng PowerShell, nhập chuỗi kết nối trực tiếp/session pooler của database demo khi được hỏi:

```powershell
$demoRestoreUrl = Read-Host 'Connection URL cua database demo RONG'
pg_restore --dbname="$demoRestoreUrl" --no-owner --no-privileges --exit-on-error --single-transaction "output/defense-2026/EquiFlow_Demo_2026_07_12.dump"
Remove-Variable demoRestoreUrl
```

Chuỗi có mật khẩu chỉ nhập tại máy của bạn; không gửi vào chat hay commit. Không thêm `--clean` và không dùng lệnh này với database đang phục vụ người dùng. Sau khi restore, cấu hình hai biến kết nối của BE vào database demo rồi chạy:

```powershell
npx prisma generate
npx ts-node test/seed-lifecycle.check.ts
```

**Muốn giữ dữ liệu đang dùng:** sao lưu database trước, sau đó chỉ chạy `npm run db:seed` không có `--reset`. Seed không ghi đè toàn bộ các bản ghi trùng ID, nên các ngày giải/giá trị hóa đơn cũ đã có sẽ không tự biến thành bộ mẫu mới. Có một thao tác dọn có chủ đích: xóa tối đa 22 hóa đơn kỳ 11–12 có đúng ID cố định của seed cũ. Hóa đơn ID khác được giữ, kể cả nếu kỳ của chúng là 11–12. Nếu đã sửa các hóa đơn seed cũ, chọn database demo mới thay vì dọn trên dữ liệu hiện tại.

`--reset` trong môi trường development xóa dữ liệu toàn bộ 36 bảng trước khi seed lại, gồm tài khoản và phiên đăng nhập. Chốt chặn production phụ thuộc `NODE_ENV`; đừng đổi biến sang development để chạy reset trên database thật.

Checker dữ liệu mẫu kiểm tra cả enum và kỳ hóa đơn cố định, nên chỉ dùng cho database demo; database nghiệp vụ thật có dữ liệu khác bộ mẫu có thể không đạt checker này.

## 4. Chạy local để dự phòng

1. Khởi động PostgreSQL của bạn hoặc dùng database demo riêng đã chuẩn bị. Database local cấu hình cũ ở `localhost:5432` chưa truy cập được trong lần kiểm tra này.
2. BE `.env`: `NODE_ENV=development`, `PORT=3000`, `FRONTEND_URL=http://localhost:5173`, hai URL database trỏ đúng database demo. Giữ các JWT secret hợp lệ đang dùng. Nếu chỉ demo đăng nhập mật khẩu, có thể dùng email mock ở local.
3. Trong BE chạy `npm run start:dev`. Kiểm tra `http://localhost:3000/api/health` trả JSON và `database.connected=true`.
4. FE `.env`: `VITE_API_URL=http://localhost:3000/api`, `VITE_USE_MOCK=false`. Trong FE chạy `npm ci`, rồi `npm run dev -- --host localhost --port 5173 --strictPort`.
5. Mở `http://localhost:5173/login`, đăng nhập tài khoản mẫu. Restart Vite sau khi đổi `.env`.

Local dự phòng chỉ hoạt động không cần Internet nếu PostgreSQL cũng chạy local. Không trỏ local về database thật để diễn tập các thao tác ghi.

## 5. Deploy website hiện tại

Theo hướng dẫn triển khai sẵn có trong repo: FE dùng Vercel; BE dùng Render/Docker; database dùng Supabase. Đã kiểm tra công khai `https://tmec.site` trả trang web và `https://api.tmec.site/api/health` trả JSON, database connected, ngày 18/11/2026. Chưa đăng nhập dashboard của các nhà cung cấp để xác minh cấu hình tài khoản.

1. Sao lưu database đang dùng bằng công cụ backup của bạn hoặc `pg_dump`. Ghi lại deployment/commit trước đó và nơi lưu hai URL database cũ ở chỗ riêng. Không đưa secret vào Git.
2. Review, commit và push **cả hai repo**. Hai checkout hiện ở nhánh `dev`; kiểm tra branch nào được Vercel/Render cấu hình deploy. Nếu dịch vụ theo dõi `main`, push `dev` một mình không cập nhật web.
3. Render: giữ Dockerfile hiện tại. Cấu hình `NODE_ENV=production`, `FRONTEND_URL=https://tmec.site`; giữ `SIMULATOR_URL` đúng tên miền simulator đang dùng. Dùng hai URL của database demo mới nếu chọn thay bộ mẫu; bảo toàn JWT/Google/email secret hiện tại. `DEV_FIXED_OTP=false`; email thật dùng provider đã cấu hình.
4. Dockerfile build Prisma Client và BE; khi khởi động dùng `db push --skip-generate`, rồi chỉ tự seed nếu bảng User rỗng. Database đã có tài khoản sẽ **không tự seed lại** sau mỗi deploy. Nếu dùng database mới đã nạp sẵn thì không cần seed nữa. Nếu chọn giữ database cũ và bổ sung fixture, chạy `npm run db:seed` đúng một lần trong Render Shell, sau khi backup; tuyệt đối không thêm `--reset`.
5. Chờ BE healthy ở `https://api.tmec.site/api/health`, rồi deploy FE. FE build `npm run build`, output `dist`, `VITE_API_URL=https://api.tmec.site/api`, `VITE_USE_MOCK=false`. Biến Vite được đóng vào bundle lúc build; đổi biến xong phải redeploy FE.
6. Hard refresh trình duyệt hoặc dùng cửa sổ ẩn danh rồi đăng nhập lại. Mở Swagger `https://api.tmec.site/api/docs`: không còn tag AI Assistant. Mở `/assistant`: không còn trang trợ lý.

Không kiểm tra API bằng `https://tmec.site/api/health`: tên miền FE có thể trả HTML của React do fallback. Phải dùng `api.tmec.site`.

Quay lại nếu có lỗi: rollback deployment FE/BE về bản cũ; nếu vừa chuyển sang database demo mới thì đổi cả hai URL về database cũ và restart BE. Database cũ được giữ nguyên. Với thao tác seed trực tiếp vào database cũ, rollback code không hoàn tác dữ liệu đã sửa/xóa; phải dùng backup.
